# SDLC plugin against the evidence (2026-09-30)

Scope: every mechanism in `~/projects/skills/skills/SDLC/` and `~/projects/skills/plugins/SDLC/`, judged against three kinds of source: the web (papers, lab posts, practitioner write-ups), the user's warehouse (`feeds.articles`, 105,762 rows fetched 2026-06-20 to 2026-09-30, searched by title regex, one query per mechanism), and the experiment in this directory (`RESULTS.md`, `runs/*/grade.json`, the judge files, and the SDLC runs' review artifacts under `runs/*-sdlc-*/repo/.git/worktrees/*/`). Sources are numbered; the full list with dates and URLs is in section 5. `E` sources are this experiment. The fourth experimental arm, the careful prompt on a copy of the llama.cpp checkout that `SDLC:guardrails` had set up (a 2,783-line commit: `AGENTS.md` rewrite, `./check`, the bash, main, tests, push and deps guards, fast-check and turn-end-check hooks, a pre-commit gate, Semgrep rules and complexity ratchets; built once in 44 minutes for $8.92), landed while this was written and is cited as E6.

## 1. Verdict

The evidence supports the user's position on cost and on structure and does not support it on two details. Measured on 2026-generation models, the parts of SDLC that have evidence behind them are: a concrete specification before code (resolve rate 54.8% to 70.8% on SWE-bench Verified when the issue text is hidden versus shown, Sonnet 4.5 [85]), tests written from the specification by an agent that has not seen the implementation (fault detection 25% versus 14% when the same model writes tests after its own code [58]; 100% versus 62% correct final code with a spec-grounded test checklist [59]), tests the agent cannot edit plus an instruction to stop and report when a test looks wrong (circumvention of a locked test file falls from 40-94% to zero only when the stop instruction is present [71]), one review by an agent with no builder context (a byte-identical error is flagged 23-93 points more often when it arrives as external input than as the model's own output [35]), and one verification pass over the reviewer's findings (precision 0.353 to 0.471 [39]). The parts with evidence against them are: a second review round on the same change (F1 0.376 to 0.303, 62% more false positives [50]), separate role agents at equal budget (0.769 versus 0.754, p = 0.80 [47]), a refuter on a different model as a rule (a weaker reviewing model subtracted 8.6 points [38]), style instructions injected into every agent (up to 12 points of pass@1 lost on weaker models, none on stronger [10]), and a tracker in the loop (no measurement at all). The experiment here agrees: the one-paragraph careful prompt, which contains exactly the supported parts, tied plain prompting on hidden tests (45/50 versus 44/50) and ranked best with the blind judge (2.8 of 7), while the full SDLC loop, which adds the unsupported parts, tied on hidden tests (43/50), ranked worst (4.1), and cost 7-10 times more [E1]. Two details of the user's position are not supported: "the agent loves to write bad tests" holds for bulk zero-shot test generation (62-93% of test files with weak assertions by LLM judge, Sonnet 4.5 [64]) but not for tests written turn by turn in real development on Sonnet 4.6 (per-test mutation kill rate 53.2% versus 48.0% for Django's own tests [65]), so the mitigation is where the tests come from (the spec, a separate context), not more test-writing instructions; and "hooks may not be needed" runs against the only direct evidence, which is that prose rules in CLAUDE.md scored 0-12.5% compliance on behaviour changes where a tool or hook scored 100% [24], that an Opus 4.6 session bypassed a prose and a settings-level "no --no-verify" rule across six commits [11], and that Anthropic's own current guidance calls CLAUDE.md "advisory" and hooks "deterministic" [21]. What is unsupported is the number of hooks, not their existence: the measured effects come from a locked test directory, a runnable check, and a merge or push deny, not from edit-time, turn-end and session-start hooks together. The guardrails arm here does not settle the hooks question either way: on llama.cpp the full `guardrails` setup under the careful prompt passed the same 10 of 10 hidden tests, broke the same 3 existing tests that the careful and plain runs broke, refused no tool call, and cost $7.15 and $21.66 against $8.27 and $12.95 without it [E6]. The hooks ran on every call and passed silently, and most of them had nothing to see: the accepted-test guard acts only on red commits that `deliver`'s `story.sh` records, so without `deliver` it exits at once; the main-branch guard never fired because both runs branched before their first edit; and the Edit-matched hooks (main guard, tests guard, fast-check) saw 15 and 3 Edit calls against 117 and 115 Bash calls for about 500 changed lines each, so most code was written through Bash heredocs or scripts, which those hooks never see [E6]. The divergence that broke the 3 tests was a reading of the story ("`until`, `rest` and the like") that no check can see, and the one thing that would have caught it, a test pinning the `any` parser's current behaviour before the change, is a story-level step, not a hook.

## 3. The proposed rewrite

### 3a. An agile planning plugin for stories

* **What the evidence supports:** a concrete specification before code, and questions only where the agent's interpretations diverge. The measured gain is on underspecified requests: 54.8% to 70.8% resolve rate when the issue text is restored [85], 16 points recovered by uncertainty-gated questions [85, 86], and fewer refinement turns when the agent asks before planning [91]. On a request that is already concrete the gain is not measurable: this experiment's stories named the public API and exact strings, and the criteria step added nothing [E1]; five reviewers with a spec found no more bugs [96]; a spec pipeline cost 10x on a CRUD feature [87]. What is inside a good spec is measured more precisely than its format: an enumerated list of cases beat prose (30 of 30 planted bugs versus 27 of 30) and both beat decomposition without a spec (2 of 30) [59]; "what is out of scope" and "an end-to-end verification step" are Anthropic's two named spec contents [21]; a "reproduce, then abstain or fix" line for bug reports raised correct abstention from 65.0% to 80.5% on Sonnet 4.6 [93].
* **What the evidence does not support:** the card ceremony. No study measures Given/When/Then against prose, owner agreement parked on an issue, product-choice limits per story, story maps, release lines or walking skeletons as agent inputs. User stories written by LLMs meet acceptance quality criteria less often than human-written ones [100], so the user writing the outcome line is consistent with the evidence, but nothing measures it.
* **Design the evidence supports:** one skill, `story`, that turns a request into one Markdown story in the repository or the chat: an outcome sentence, a `Not doing` list, an enumerated list of cases with concrete values (each case one line, the failure paths walked as `setup.md` section 2 already does), and one `Verify` line naming the command or screen that shows the outcome. Ask a question only when two readings of the request lead to different cases, with the recommended reading first (Claude Code's `AskUserQuestion`), and otherwise decide and list the decision. Size first: a one-sentence diff gets no story (Anthropic's rule [21]). Keep the epic skill's split patterns as a short reference for a request that is several stories, and drop the tracker, the header lines, the release line and the owner parking from the default path. The feature acceptance test the user writes stays, with one caution: give it to the agent as a check to run at the end, not as the specification, because agents given the acceptance oracle built to the oracle and left the requested library dead [88].

### 3b. Test-first, with a mitigation for bad tests

* **What the evidence supports:** tests written from the specification by a context that has not seen the implementation, locked once written, with an instruction to stop and report when a test looks wrong. The mechanism is error propagation: tests written after the same model's code detect 14% of faults against 25% before [58]; over 99% of generated tests encode the pre-change behaviour [67]; a verifier that saw the repair loop is more lenient [36]. The fix is where the tests come from, not an instruction to do TDD: a prose "do TDD" raised regressions [60], a TDD prompt scored below average on hidden tests [61], and more or fewer agent tests changed nothing [62]. Supplying correct tests lifted SWE-bench Verified 68.0% to 94.3% [57], which is the nearest measurement of a human-approved test list. On tampering, Opus 5.5's measured rate is the lowest of its generation (11.2% on CheatBench [74]; 0.63% of training episodes [19]), but a locked test file alone still left 40-94% circumvention on Opus 4.6, Sonnet 4.6 and GPT-5.4, and only "stop and report" drove it to zero [71]. On weak tests: bulk-generated suites are weak (62-93% of files with weak assertions [64]; 36% of agent test commits add mocks versus 26% human [66]), but tests written turn by turn on a real repository by Sonnet 4.6 matched Django's own on mutation kill rate [65]; the surviving weakness in all three corpora was a loose-bound oracle, which the spec-grounded checklist fixes (false alarms 33% to 0%, 0 of 37 wrong expected values [59]). LLM-designed mutants find real bugs 1.75x as often as tool mutants [80] and are harder to kill [63], at the cost of 20-25% uncompilable and 3-6% equivalent mutants.
* **What the evidence does not support:** seven generator classes and a competitor patch per row verified by a second agent. In this experiment the tables produced 1.5-3x the test lines of plain prompting, the same hidden-test misses, and a judge "tests" score equal to plain [E1, E4]; `story.sh kill` ran in 3 of 10 runs and found two blind tests, neither a hidden miss [E2].
* **Design the evidence supports:** a fresh subagent (`test-author`) gets the story and the repository, not the chat, and returns a numbered test list (one line per case, the fixture value, and for each the one wrong implementation it rejects) and the test files, committed as the red commit. The user approves or edits the list in one message when present; when absent the list stands. Then lock: keep `tests-guard.sh` and `accepted_tests.py` as they are, and add one sentence to the builder's prompt: "A test you cannot satisfy for a reason that holds against the code is a stop: report the test and the reason and make no change to it." Implement in the main session or one builder agent with the preservation sentence from [92]. Before finishing, run one mutation pass over the changed files with the language's tool where one exists (`mutmut`, `stryker`, `go-mutesting`, PITest), and for each row's named wrong implementation apply it once by hand only when no tool exists; a survivor is one more test, not a review finding to refute. Drop the Seam, Type, Cardinality, Both sides and Budget generator rows as prompt text and keep the blind-fixture list (batch of one, identity value, sorted input, two calls for a race) as the test author's checklist, since those are the fixtures the loose-bound oracle finding [65] and the fixture study [59] point at.

### 3c. Implementation, then a review subagent

* **What the evidence supports:** one reviewer in a fresh context, writing tests from the criteria before reading the build, followed by one verification pass over its findings, then one fix pass. Fresh context is the active ingredient: 23-93 points more explicit correction when the error arrives as external input [35]; Claude self-review of Claude code gained 0 points [38]. A reviewer that writes tests from the specification alone found 589-906 bugs official suites missed at under 1.87% false discovery, on Claude Code with Opus 4.8 [81]. A verification stage raised precision 0.353 to 0.471 [39]; a critic that must disagree raised LiveCodeBench 77% to 87% where a plain second reviewer added nothing [37]; Anthropic's Code Review reports under 1% of findings marked wrong after its verification step [28]. In this experiment the careful arm's one reviewer found a real behaviour bug in 2 of 8 runs and weak tests in 5 of 8 for about $1.50 and 3 minutes per run [E3], and SDLC's reviewer found real non-blocking defects [E2]; neither found the unstated edge cases, which only the story could have supplied.
* **What the evidence does not support:** a second review round (F1 falls 0.376 to 0.303 with 62% more false positives [50]; per-round F1 falls after round 2 on real reviews [33]; iterative feedback doubled evasion [106]), a refuter on a different model as a rule (asymmetric: -8.6 points when the weaker reviewer judges [38]; critic null in 2 of 5 pairings [40]; judge-swap effect at most 2 points [29]), a separate refactor agent (no measurement; the preservation sentence in the builder's prompt is measured [92]), a security agent on every diff (near chance on realistic SAST output [41]; no confirmed finding in 6 runs here [E2]), and role-split setup/build agents (equal-cost ablation null [47]; delegation 66% versus single agent 86% [49]). A reviewer told to find gaps "will usually report some, even when the work is sound", and "chasing every finding leads to over-engineering" [21].
* **Design the evidence supports:** after the suite is green, launch one `review` agent with the story, the branch, the red commit hash and the check command. Its prompt has three parts in this order: write attack tests from the story's cases through the public interface before reading the diff; then read the diff and list every finding as `file:line`, the input that breaks it, and either a red test path or the line read; then diff the accepted tests against the red commit. A finding with neither a red test nor a cited line is dropped by the same agent in a second numbered pass ("for each row, name the line that stops it or keep it"), which is the verification stage [39] without a second launch; run it on a different model only when that model reviews at least as well as the finder, which on current numbers means Opus or Sonnet 5.5 either way [104]. The main session fixes confirmed findings in one pass and runs the suite; a finding that survives the fix is a question to the user, not a third round. Run the security prompt only when the diff adds an entry, a sink or a credential (the `Security:` trigger in `review.md` section 8 already encodes this). Keep the 550-word description as a plain summary written by the main session.

## 4. Experiments still needed

Each fits `run.sh`, `grade.py` and `judge.py` as they are, with one new arm name and, where noted, one prompt line or one hook. Run 5 repetitions per arm, not 2: run-to-run standard deviation exceeds 1.5 points at temperature 0 from infrastructure alone [2608.13867 in the warehouse], and the arms here differ by 1-2 hidden tests.

* **Underspecified stories (settles row 1 and section 3a):** replace each `tasks/<task>/story.md` with the upstream issue text as filed, before the maintainer's clarifications, and run `plain`, `careful` and a `story` arm whose prompt adds "write the cases this must handle as a numbered list with concrete values and a Not doing list before any code". Grade on the same hidden tests. The expected gap, from [85], is about 15 points for plain on hidden issues and most of it recovered by the story arm.
* **Test author in a fresh context (settles section 3b):** `careful-split`: the careful prompt, with "have a fresh subagent write the failing tests from the requirements alone, commit them, then implement" replacing "write failing tests". Compare hidden tests and the number of accepted tests the main session edited after the red commit.
* **Locked tests plus stop instruction (settles row 4):** `careful-lock`: install only `tests-guard.sh` and `accepted_tests.py` and add the stop sentence. Count test-file edits after the red commit, hidden tests and cost. Run it on the llama task, where 3 of 4 cheaper runs changed existing test expectations.
* **Mutation pass (settles rows 5 and 6):** `careful-mutate`: careful plus "before finishing, run the project's mutation tool over the files you changed and add a test for each survivor". Grade hidden tests, survivor count, test lines and cost against `careful`.
* **Review ablation (settles rows 11, 12 and 14):** four arms on the same tasks: `careful-noreview` (the careful prompt with the review sentence removed), `careful` (one review), `careful-verify` (one review plus the numbered verification pass), `careful-two-rounds`. Count confirmed findings per run and hidden-test change per finding. The prediction from [50] and [37] is that `careful-verify` beats `careful` on judge rank and `careful-two-rounds` costs more with no hidden-test change.
* **Guardrails separated (settles rows 23-26; the landed arm answers only the sum, and on one task):** on the `llama-harness-0` checkout, two more arms: `AGENTS.md` only (hooks and gate removed) and hooks only (`AGENTS.md` reverted to upstream). The `llamah-careful-*` runs are the "both" arm and showed no change in hidden tests or regressions, but their Edit-matched hooks saw 15 and 3 of about 500 changed lines because the rest went through Bash, and the accepted-test guard was inert without `deliver` [E6]. Before rerunning, match the main, tests and fast-check hooks on `Bash` as well (parse the command for a write to a tracked file, or run the check on `git status` output at `Stop`), and make the accepted-test guard read a red-commit marker the careful prompt can set (`git config branch.<branch>.redCommit <hash>` after the test commit). Count, per run, each hook's invocations and its denials from `--include-hook-events`.
* **Writing rules (settles row 22):** `careful-writing`: the careful prompt in a session with `plugins/SDLC/hooks/hooks.json`'s `SessionStart` and `SubagentStart` hooks loaded and nothing else from the plugin. Compare cost, hidden tests and judge rank with `careful`.
* **Judge validity (bounds every judge number above):** have the user rank one task's seven anonymised diffs blind and compare with `judge-<task>-*.json`; then rerun the judge on one SDLC diff with its test files cut to the plain arm's length to see how much of the rank gap is volume. * **Characterization first (settles row 8):** on the llama task only, `careful-pin`: "before changing a parser, add a test that pins its current behaviour on invalid bytes". Count regressions of upstream's `any` tests.
