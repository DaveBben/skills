# Step: build

A **row** is one test in the story's test table in `card.md`; a **red row** fails until the build makes it pass. The **user's turn** is one piece of the story the user does by hand: a **core**, one small function holding a decision, written after the build, or a **sketch**, pseudocode for the story's structure, written before it. The setup's `Yours:` line proposes one, or says none.

When `Yours:` is not none, offer the user's turn first or last by its mode, in one message that names the mode the setup proposed; one word switches it ("core", "sketch") or skips it ("skip"), with no reason asked. Doing it is the default. Never offer it after the user said they are leaving, overloaded, or not to ask for input: the `build` agent does that part and the log records it skipped.

* **Sketch, before the build:** the message gives the file holding the `TODO(user): sketch` marker and the failing tests. When the user says done, a fresh `review` agent reviews the sketch, then a fresh `refute` agent judges its rows; send the surviving `teach` rows to the user as the review wrote them, `wrong` rows first, then `unverified`, then `shape`, never rewritten code. A surviving `question` row parks the story as a product decision, asked as the waiting question. The user revises the sketch or says build. The `build` agent then builds every red row from the sketch, and its `Departed:` lines, each place the code decided what the sketch left open or overrode it, go to the user with the review's result.
* **Core, after the build:** the `build` agent builds every red row except the core. Then relay the setup's `Yours:` line to the user with the core test's path and name from the setup's `Red:` line. When the user says done, the `build` agent runs the suite and commits the change as it stands, with the message `yours: <row title>`; a red result goes back to the user with its failure lines.

The `build` agent gets the setup's `Red:`, `Paths:`, `Non-negotiable:` and `Yours:` lines. Skip it when no row is red. When the user says they will write the story's code themselves, skip it and wait for their commit. The review waits for the user's turn; meanwhile set up the next ready story, up to the number of stories at once `AGENTS.md` states. A question about something a person sees is parked. A build that returns with a row still failing, or that changed a file outside its paths: reset to the latest red commit and reissue with the one new fact. Red twice on sound rows is a split. A row the builder cannot satisfy for a reason that holds against the code is a wrong row: run `story.sh next wrong-row`.

When every red row passes, run `story.sh next review`.
