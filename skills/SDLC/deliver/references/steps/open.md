# Step: pull request open

* **Watch this feature's open pull requests** for merges, failing checks, review comments and conflicts with main. Rebase a story branch under the grant with `story.sh rebase`, with the `build` agent resolving any conflict. Before launching a rebase or a red-row agent, read the target branch's head: a merge or a force-push since the last read changes the task. The agent never merges. A watch set up in this session stops with the session: say so when starting it; a later session resumes from `story.sh status` and the epic.
* **Other pull requests:** watching them needs the user to name them; "all my open pull requests" names them, and acting on any of them beyond reading is asked, naming exactly which. Outside this feature, rebase a pull request only after the user has granted it by name, with plain git, and park it when it conflicts; conflicts are resolved alone only on story branches.
* **Review comments:** the `lookup` agent returns each new comment's claim, with its file and line. One `refute` agent per pull request checks every one that claims how the code behaves against the code. A confirmed defect becomes a red row, a test that fails until the build fixes it, as `story.sh next verdicts` says. Then the `description` agent drafts the reply, given the comments, the verdicts and the branch. The `refute` agent checks every claim in the draft about how code, a service or data behaves, given every repository the text names. Show the user the reply; the user posts it, or says to.
* **Closed without merging:** ask the user whether to reopen it or cut the story. A cut story runs `story.sh close <branch>`, and a `worker` closes its issue with the reason as its resolution.
* **On merge,** run `story.sh close <branch>` unless `status` already closed it, and have a `worker` append the merge time to the log comment's `Cycle:` line and set the story Done with its log comment as the resolution. When the story's `Success` signal is read after its deploy, a `worker` writes it as a second comment, `- Observed: seen <date>, <signal> = <value>`.
* **Next story:** set up the next ready story. A story is ready when every blocker is done (a spike is done when its findings comment is written), no question on it is unanswered, its comments hold no answer its description lacks, and no `story/{slug}/{key}-*` branch exists. Take stories above the release line (the header's `Release:` list) first, then the tracker's rank. Move a story ahead only because it is the walking skeleton and no story has reached a real deploy yet, a spike's answer changes other stories, or it unblocks more stories; say which. When nothing is ready and nothing is building, say which blocker frees the most and wait.
